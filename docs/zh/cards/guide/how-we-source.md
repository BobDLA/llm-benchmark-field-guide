# 这些卡片怎么取材

这套站点以“benchmark 解释卡”为目标，重点提供结构化解读与来源说明。所以来源不能只看一个排行榜，也不能只抄论文摘要。

我们现在采用一套固定的**来源梯度**，并把 repo 文档 / wiki 类资料正式纳入取材范围。

## 来源梯度

### L1. 官方发布页 / 官方项目页

优先回答这些问题：

- 这个 benchmark 是谁发布的
- 官方怎么定义它的目标能力
- 当前官方推荐读哪个版本 / 子集 / leaderboard

这类来源最适合确定：

- 名称
- 发布时间
- benchmark 家族版本
- 官方主张的“它在测什么”

## L2. 官方论文 / 预印本

优先回答这些问题：

- 数据是怎么构造的
- 输入输出格式是什么
- 判分方法是什么
- 作者自己承认了哪些边界

这类来源最适合确定：

- 数据规模
- 任务分布
- 核心指标
- 人类基线 / 官方基线

## L3. 官方 repo / 官方 dataset card / 官方 harness

优先回答这些问题：

- 实际跑分时代码怎么组织
- 输出字段到底长什么样
- 评测脚本真正怎么算分
- 版本切换会影响什么

这类来源最适合确定：

- 运行入口
- answer extraction
- exact match / pass@k / strict-loose 等实现口径
- 数据字段结构

## L4. Repo wiki / GitHub Pages 文档 / DeepWiki 这类“仓库文档层”

这是这次新增进正式方法里的来源层。

它主要用于补足：

- README 没展开写清的内部结构
- 评测流水线有哪些关键假设
- 代码目录和运行模式怎么对应
- 官方 repo 里“真正重要但藏得深”的实现细节

这层来源**不是第一定义来源**，但很适合解释：

- 这个 benchmark 在工程上到底怎么跑
- 为什么它的分数口径会受某些实现细节影响
- 哪些目录 / 脚本才是“真正有解释价值”的部分

> [!TIP]
> 这层信息最适合补“怎么运作”与“为什么要小心解读分数”，不适合单独拿来定义 benchmark。

## L5. 社区 issue / 讨论串 / 更正说明

只在两个场景下使用：

- 官方自己承认或接受了某个问题
- 社区已经给出可核验的实现缺陷、污染路径或评测漏洞

这层来源只用于：

- `§5.3 缺陷 / 争议`
- `§5.4 风险表`

不会用它来定义 benchmark 的基本事实。

---

## 冲突时怎么裁决

如果不同来源口径冲突，默认按下面顺序裁决：

1. 官方发布页 / 官方 leaderboard 当前说明
2. 官方论文正文
3. 官方 repo 当前 README / dataset card / harness 实现
4. repo wiki / 文档层
5. 社区来源

如果旧论文和新 repo 不一致，会优先标注：

- “论文最初口径”
- “当前实现口径”

避免把两个版本混成一个数字。

## 每张卡片至少回答的四个来源问题

在写一张卡片之前，我们至少会核对：

1. 官方到底说它测什么，不测什么？
2. 实际输入、输出、判分在代码里怎么落地？
3. 当前最常被引用的是哪个子集 / 版本？
4. 哪些争议是官方或社区已经明确指出的？

## 目前明确不作为主来源的材料

- 只给榜单、不解释口径的聚合站
- 没有原始链接的二次转述博客
- 厂商海报图或社媒截图
- 只报“最好成绩”但不说 prompt / scaffold / sampling 的宣传材料

## 你可以怎样使用这些卡片

如果你只想快速判断一个 benchmark 值不值得看：

- 先看 `§2 快速参考`
- 再看 `§5 它可靠吗`

如果你想做真正可复现的评测方案：

- 先看 `§4 它怎么运作`
- 再回到官方 repo / dataset / 文档层核对细节

> [!IMPORTANT]
> 这套卡片默认把 benchmark 视为“测量工具”，不会把它当成“真理”。
> 所以每张卡片都会同时写它的价值和它的失真来源。
